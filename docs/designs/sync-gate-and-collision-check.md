# Design: Execute Pre-Flight Sync Gate + Live PR-Scope Collision Check

Generated by /office-hours on 2026-08-30
Branch: main
Repo: muhaiminul00/gstack-pilot
Status: APPROVED
Mode: Startup (intrapreneurship)

## Problem Statement

`gstack-pilot` coordinates one agent's task lifecycle (Commander plans → Execute
builds → PR-first wrap-up via review/qa/ship) but has no git-freshness awareness
at task start. Nothing in `execute.md` verifies the base branch is current, or
that the working tree is clean, before a task branch is created. As a second real
project (`zm-brain`) onboards teammates onto this plugin, two or more people (or
Claude sessions) working the same repo the same day can start Execute against a
stale base, or Execute can run over uncommitted changes that belong to unrelated
work.

## Demand Evidence

Not hypothetical: the user flagged a concrete fear — "high chance of
parallel-agent runs & that may collide on each other task" — while scoping this
exact change, for a team about to run `gstack-pilot` across two real repos
(Zenny, zm-brain) with a second person now onboarding. The plugin has already
been proven end-to-end via 3 real PRs on zm-brain; the next real use is multi-
person, not solo.

## Status Quo

Today, `execute.md` writes `mode.json` to `"execute"`, then goes straight to
implementation. It assumes whatever is checked out locally is a safe base. No
`git fetch`, no freshness check, no dirty-tree check, and no awareness of what
other branches/PRs are currently touching.

## Target User & Narrowest Wedge

Target: any teammate (or their Claude session) invoking `/gstack-pilot:execute`
in a repo shared with at least one other active contributor. Narrowest wedge:
two checks only — (1) a git sync gate (fetch, verify base is current, branch
from latest, stop on a dirty tree) and (2) a live, read-only PR-scope overlap
check against currently open PRs — not the full coordination layer (task-
ownership schema, hand-maintained registry, worktrees, GitHub Issues) the
external proposal that prompted this session also suggested.

## Constraints

- Must fit gstack-pilot's existing composition mechanism: file-reference
  chaining into gstack skills, PR-first wrap-up with no trivial-housekeeping
  exemption, `plugin.json`-only versioning discipline (bump on every
  user-facing change).
- Must never auto-pull/stash/switch over uncommitted work — that's the kind of
  "clever" automation that destroys someone's afternoon. Detect and stop,
  never silently resolve.
- Must degrade by disclosure, not silent skip, if `gh` CLI or GitHub
  reachability isn't available — same pattern the plugin already uses for
  "gstack not installed."
- Small team (2-3 people) with no unattended parallel-agent runs today — the
  fix must not expand into infrastructure sized for a scale not yet reached.

## Premises

1. gstack-pilot's existing merge-time model (feature branch → PR → review →
   qa → ship → merge, never direct-to-main) already solves the "shared main
   stays trustworthy" half of coordination. The gap is only at task START, not
   at merge.
2. The concrete missing piece is narrow: Execute doesn't verify the base
   branch is fresh before branching, and doesn't guard against starting work
   over an unrelated dirty working tree.
3. Heavy coordination infra (hand-maintained task-ownership registry, git
   worktrees, GitHub Issues as a second source of truth) is premature for this
   team's current scale — but a *light*, live-derived form of collision
   awareness (checking open PRs' changed files against one new structured
   `Scope` field on the Build Card, not a hand-maintained artifact) is cheap
   enough to include now, given the user's stated parallel-agent concern.
   Revised mid-session from "defer entirely" to this split after the user
   pushed back, then revised again after adversarial review found the
   original "no new schema" framing was false — a small schema addition (one
   field) is unavoidable and is included in the recommended approach.
4. GitHub Issues as an additional coordination substrate would duplicate
   Build Cards/state-doc without covering a gap that exists today.
5. Whatever gets built must fit gstack-pilot's existing composition mechanism
   rather than introducing a new mechanism.

## Approaches Considered

### Approach A: Sync gate only (no collision check)
Fetch origin, verify base is current, branch from latest, stop on a dirty
tree. No visibility into what other branches/PRs are touching.
Rejected: doesn't address the collision risk the user explicitly raised.

### Approach C: Full coordination layer
Hand-maintained `.project/coordination/active-tasks.md`, task-ownership
schema on every Build Card, git worktrees per task, GitHub Issues as
backbone — the full scope of the external proposal that prompted this
session.
Rejected: solves for a scale (heavy concurrent parallel-agent use) this team
doesn't have yet; a hand-maintained registry is a worse failure mode than no
registry (people trust a stale table more than they'd trust nothing) — exactly
the speculative-abstraction trap this project's own design principle warns
against.

## Recommended Approach

**Approach B: Sync gate + live PR-scope collision check.**

Three files change, not one — the adversarial review (below) caught that
`execute.md` alone is insufficient: Execute mode *persists* across sessions
via `.claude/hooks/state/mode.json`, and a resumed session gets its
instructions from `hooks/session-start.js`'s condensed `modeInstructions.execute`
string, which does not re-read `commands/execute.md`. Without touching both,
a teammate resuming an already-Execute session — exactly the multi-person
scenario this design exists for — never sees the new pre-flight step.

**1. `commands/execute.md`** — add a pre-flight block, positioned before the
existing "implement the approved scope" step and before any branch is
created:

1. `git status --porcelain` — if dirty, STOP. Report the exact files and ask
   the human how to proceed (commit, stash themselves, or confirm these
   changes belong to this task). Never auto-stash or auto-switch, and never
   move off the currently checked-out branch without asking first.
2. Resolve the base branch explicitly: the repo's default branch via
   `gh repo view --json defaultBranchRef`. (An override via a Build-Card-
   named integration branch is deferred — see Open Questions; `build-cards`
   has no such field today and adding one is out of scope for this card.)
   `git fetch origin`, then compare local base to `origin/<base>`. If behind,
   fast-forward (`git pull --ff-only`) before creating the task branch. If
   the fast-forward fails (base has diverged), STOP, report the divergence,
   and ask — never force, never auto-checkout.
3. Create the task branch from the now-current base. **This replaces, not
   duplicates, the existing wrap-up-chain step 2 ("commit on a feature
   branch, not the default branch")** — that step's wording changes from
   "create and commit on a feature branch" to "commit on the task branch
   already created by this pre-flight step." This design therefore also
   edits `execute.md`'s existing wrap-up-chain step 2 text, not just its
   pre-flight section — flagged explicitly so the Build Card scopes both
   edits to the same file, not just the new block.
4. If `gh` CLI is available: `gh pr list --state open --json number,headRefName,files`
   and diff the returned file paths against the current Build Card's
   `Scope` field (see build-cards change below) using exact-path-or-prefix
   matching — a listed directory matches any file under it. On any overlap,
   **stop and ask** the human whether to proceed, coordinate with the other
   PR's author, or adjust scope — a real STOP, not a printed warning an
   agent can ignore and continue past. If `gh` isn't available or the API
   call fails, disclose plainly ("PR-scope collision check unavailable —
   `gh` not found/unreachable") and fall through to step 5 without blocking.
5. Proceed to implementation as `execute.md` already defines.

**2. `hooks/session-start.js`** — extend `modeInstructions.execute`'s
condensed string with a clause naming the pre-flight requirement (same
"see this command's own file for the exact chain" pattern the wrap-up chain
already uses there), so a resumed Execute session is told the gate applies
to its current task's first branch/write action even though it wasn't just
invoked fresh.

**3. `skills/build-cards/SKILL.md`** — add one new field, `Scope`: a list of
concrete file/directory paths this card touches. This is the one schema
change the collision check actually needs (the existing fields — Target,
Dependencies — are prose, not structured paths, and can't be diffed against
PR file lists). Small, targeted addition, not a schema overhaul.

Bump `plugin.json` (minor version — new user-facing behavior, not a bugfix).

## Open Questions

- Exact wording for the STOP prompt on dirty tree / PR-scope overlap — draft
  in the Build Card, not finalized here.
- Whether the PR-scope check should also compare against other *local*
  branches (not just open PRs) — deferred; open PRs cover the realistic case
  (a teammate who hasn't pushed yet isn't visible to anyone regardless of
  what this plugin does).
- `gh` CLI is now a hard dependency of the collision check (not soft) —
  `TEAM_SETUP.md` needs a step added for it, as part of this same Build Card,
  not a follow-up.
- Whether the base branch should ever be overridable per-Build-Card (a
  project with a non-default integration branch) — deferred; would need its
  own new field on `build-cards/SKILL.md` alongside `Scope`, and no current
  project needs it yet. Default-branch-only for this card.

## Success Criteria

- A dirty working tree stops Execute before any branch/file mutation, every
  time, with the exact files named.
- A stale base is fast-forwarded (or the human is stopped and told, if it
  can't be) before the task branch is created — verified live, not assumed.
- An open PR touching overlapping files triggers a real stop-and-ask, not a
  warning that's easy to skip past.
- Missing `gh` CLI is disclosed in plain language, never silently skipped.
- A session resumed mid-Execute (not freshly invoked) still surfaces the
  pre-flight requirement, verified by reading `session-start.js`'s
  `modeInstructions.execute` string directly, not assumed from `execute.md`
  alone.
- `Scope` field is live in `build-cards/SKILL.md` and actually used by the
  diff in step 4 — verified by running the collision check against a real
  open PR with overlapping paths during Execute's own build-verify pass.

## Dependencies

- `gh` CLI presence — hard dependency for the collision check (soft-degrades
  to disclosure-only if unavailable, per step 4, but must be documented as an
  expected install in `TEAM_SETUP.md`, not left implicit).
- New `Scope` field added to `build-cards/SKILL.md` as part of this same
  Build Card — the collision check cannot run without it; this is not an
  existing field being reused.

## Reviewer Concerns

Surfaced by the adversarial review's third (final, cap-reached) pass — score
8/10, up from 6/10 across three rounds. Neither requires re-scoping the
approach; both are normal `/plan-eng-review`-level tightening:

- The Recommended Approach's quote of `execute.md`'s current wrap-up-chain
  step 2 ("create and commit on a feature branch") paraphrases loosely — the
  live text actually reads "Commit on a feature branch, not the default
  branch," with no "create." The substance of the reconciliation (branch now
  created earlier, by the pre-flight step, so step 2 becomes commit-only) is
  correct; the quoted "before" text should be corrected to the real wording
  before this becomes a diff instruction.
- Two mechanics are implied but not stated: (1) whether the base branch needs
  to be checked out before `git pull --ff-only` lands the fast-forward on the
  right ref, or whether `git fetch origin <base>:<base>` (no checkout) is the
  intended form; (2) whether step 3's "create the task branch" skips
  branch-creation on a resumed session that already has one, or always
  creates. `session-start.js`'s clause implies skip-if-exists but step 3's
  own wording doesn't say so explicitly.
